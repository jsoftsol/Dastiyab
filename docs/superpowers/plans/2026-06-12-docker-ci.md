# Docker + CI/CD Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add production Docker configuration and a GitHub Actions CI/CD pipeline so that pushing to the `deploy` branch rebuilds and restarts the app on a VPS.

**Architecture:** Multi-stage Dockerfile (deps → builder → runner) produces a minimal Node 24 image running Next.js standalone. Three production containers: `postgres`, `app`, `migrate`. GitHub Actions rsync code to the VPS then SSH in to docker compose up + migrate.

**Tech Stack:** Docker, Docker Compose v2, GitHub Actions, Node 24 alpine, PostgreSQL 17 alpine, Prisma 7 migrate

### Task 4: Create Dockerfile

**Files:**
- Create: `Dockerfile`

- [ ] **Step 1: Create Dockerfile**

Create `Dockerfile` at the project root:

```dockerfile
FROM node:24-alpine AS deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci

FROM node:24-alpine AS builder
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
RUN mkdir -p public
COPY . .
RUN npx prisma generate
RUN npm run build

FROM node:24-alpine AS runner
WORKDIR /app
ENV NODE_ENV=production

RUN addgroup --system --gid 1001 nodejs \
    && adduser --system --uid 1001 nextjs

COPY --from=builder --chown=nextjs:nodejs /app/.next/standalone ./
COPY --from=builder --chown=nextjs:nodejs /app/.next/static ./.next/static
COPY --from=builder --chown=nextjs:nodejs /app/public ./public
COPY --from=builder --chown=nextjs:nodejs /app/prisma/generated ./prisma/generated

USER nextjs
EXPOSE 3000
ENV PORT=3000
CMD ["node", "server.js"]
```

Notes on key decisions:
- `RUN mkdir -p public` — ensures `public/` exists in builder even if the local repo has only `.gitkeep`
- `COPY prisma/generated` — explicitly copies the generated Prisma client into the runner image alongside the standalone output, since `lib/prisma.js` imports from `../prisma/generated/prisma/client.ts`
- `builder` stage is used by the `migrate` service in docker-compose.prod.yml (it has Node + Prisma CLI + migration files)

- [ ] **Step 2: Build the image to verify the Dockerfile is valid**


Expected: build completes successfully. All three stages (deps, builder, runner) should complete without errors.

If build fails on `npx prisma generate`, verify `prisma/schema.prisma` exists and `prisma.config.ts` is present.

### Task 5: Create docker-compose.prod.yml

**Files:**
- Create: `docker-compose.prod.yml`

- [ ] **Step 1: Create docker-compose.prod.yml**

Create `docker-compose.prod.yml` at the project root:

```yaml
name: dastiyab

services:
  postgres:
    image: postgres:17-alpine
    container_name: dastiyab_postgres
    env_file: .env.production
    volumes:
      - dastiyab_postgres_data:/var/lib/postgresql/data
    restart: unless-stopped
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${POSTGRES_USER} -d ${POSTGRES_DB}"]
      interval: 5s
      timeout: 5s
      retries: 5

  app:
    build:
      context: .
      target: runner
    container_name: dastiyab_app
    env_file: .env.production
    ports:
      - "127.0.0.1:${APP_PORT:-7000}:3000"
    depends_on:
      postgres:
        condition: service_healthy
    restart: unless-stopped

  migrate:
    build:
      context: .
      target: builder
    container_name: dastiyab_migrate
    command: ["npx", "prisma", "migrate", "deploy"]
    env_file: .env.production
    depends_on:
      postgres:
        condition: service_healthy

volumes:
  dastiyab_postgres_data:
```

Notes:
- `postgres` uses a healthcheck so `app` and `migrate` wait until the DB accepts connections
- `migrate` uses the `builder` stage which has the Prisma CLI and `prisma/migrations/` baked in
- `app` binds to `127.0.0.1` only — access through a reverse proxy (Nginx/Caddy)
- `APP_PORT` defaults to 7000 — override in `.env.production` if needed
- `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` are read from `.env.production` by the postgres container

Expected: outputs the resolved YAML with no errors. Warnings about `.env.production` not existing are fine at this stage.

### Task 7: Create GitHub Actions deploy workflow

**Files:**
- Create: `.github/workflows/deploy.yml`

- [ ] **Step 1: Create the workflow directory**

```bash
mkdir -p .github/workflows
```

- [ ] **Step 2: Create deploy.yml**

Create `.github/workflows/deploy.yml`:

```yaml
name: Deploy

on:
  push:
    branches:
      - deploy
  workflow_dispatch:

jobs:
  deploy:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Sync files to server
        uses: burnett01/rsync-deployments@7.0.1
        with:
          switches: -avzr --delete --exclude='.git' --exclude='.github' --exclude='node_modules' --exclude='.next' --exclude='.env*'
          path: ./
          remote_path: ${{ secrets.SERVER_APP_DIR }}/release/
          remote_host: ${{ secrets.SERVER_HOST }}
          remote_user: ${{ secrets.SERVER_USER }}
          remote_key: ${{ secrets.SERVER_SSH_KEY }}

      - name: Deploy
        uses: appleboy/ssh-action@v1.0.3
        with:
          host: ${{ secrets.SERVER_HOST }}
          username: ${{ secrets.SERVER_USER }}
          key: ${{ secrets.SERVER_SSH_KEY }}
          script: |
            cd ${{ secrets.SERVER_APP_DIR }}/release
            echo "${{ secrets.PRODUCTION_ENV }}" > .env.production
            docker compose --env-file .env.production -f docker-compose.prod.yml up -d --build
            docker compose --env-file .env.production -f docker-compose.prod.yml run --rm migrate
            docker image prune -f
```

Notes on the deploy script:
- Files land in `$SERVER_APP_DIR/release/` on the VPS
- `.env.production` is written fresh each deploy from the `PRODUCTION_ENV` secret
- `docker compose up -d --build` rebuilds and starts `postgres` and `app`
- `docker compose run --rm migrate` runs migrations after postgres is healthy, then exits
- `docker image prune -f` removes dangling images to reclaim disk space
- The `PRODUCTION_ENV` secret must include all vars from `.env.example` plus `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`

3. `$SERVER_APP_DIR/release/` directory exists on VPS (create with `mkdir -p`)
4. All 5 GitHub secrets configured in the repository settings
5. Push a commit to the `deploy` branch to trigger the first deployment
6. On first deploy, the `migrate` container runs `prisma migrate deploy` applying the initial migration and creating all tables
